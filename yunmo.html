전체 그림

독자의 노출·클릭·읽기 기록은 로깅 서버를 거쳐 GCS에 5분 단위로 쌓인다. 피처 DAG가 이것을 BigQuery에서 원본 → 정제 → 집계 → 피처로 바꾸고, 모델도 학습한다. DAG는 서빙용 피처를 파일로 GCS에 내보낸다. 점선 안의 추론 서버는 이 파일과 학습된 모델을 불러 두고, 피드 요청이 올 때마다 후보 10~20개에 점수를 매긴다. Redis는 멘토 확인 전까지 MVP에서 뺐다(WBS Q8). 굵은 테두리가 처리·피처·모델 파트가 만드는 부분이다.

결정 필요

후보 수 10~20개는 팀 계획(#14)을 따랐다. 후보가 적으면 점수화 모델이 바꿀 수 있는 순서도 적다. 후보 생성 품질이 전체 성능을 좌우하므로, 수를 늘릴지 데이터를 본 뒤 다시 정한다.

결정 필요

후보 10~20개를 누가 고르는지. WBS Q2 예시처럼 뉴스 WAS가 후보를 골라 추론 서버에 보낼지, 추론 서버가 직접 고를지 정해야 한다.

STEP 1평가 지표 정의 #23

팀 합의대로 CTR을 먼저 정의하고 순위 지표(nDCG@K)는 그 다음에 붙인다. CTR은 계산이 단순하고 baseline 피드만 있어도 바로 잴 수 있기 때문이다.

순서지표계산쓰는 곳

이후체류 시간, 읽기 완료율클릭 후 기사 페이지에 머문 시간낚시성 클릭 확인

결정 필요

CTR의 분모가 되는 "노출"의 기준을 세호 님과 맞춰야 한다. 화면에 일부만 보인 카드도 노출로 셀지에 따라 CTR이 크게 달라진다.

결정 필요

최적화 목표를 클릭 하나로 둘지, 체류 시간을 섞을지 정해야 한다. 클릭만 쫓으면 자극적인 제목이 위로 올라온다.

문제·불확실

합성 데이터에서 나온 성능 숫자는 실제 독자에게서의 성능을 뜻하지 않는다. 발표에서 어떻게 해석할지 멘토님께 확인한다.

이렇게 뽑은 이벤트는 impression, click, read_end, visit, subscribe/unsubscribe, like/unlike이다. read_end는 위 피처에는 없지만 체류 시간 지표(STEP 1)와 봇 탐지(STEP 3)에 쓴다.

구독과 좋아요는 누르는 즉시 화면에 보여야 하므로 두 길로 보낸다. 뉴스 WAS가 Cloud SQL의 subscriptions, likes 테이블에 바로 쓰고(현재 상태), 같은 순간 로깅 서버에도 이벤트를 남긴다(피처용 기록). 추천 순서에도 바로 반영하려면 뉴스 WAS가 추론 서버를 부를 때 구독 언론사 목록을 함께 넘긴다(STEP 10).

모든 사용자 이벤트에 공통으로 필요한 필드는 event_id, user_id(또는 익명 ID), session_id, event_time, model_version이다.

문제·불확실

익명 독자 식별은 세호 님 안을 따른다. 브라우저 쿠키에 임의 토큰을 넣고 서버가 그 토큰으로 reader_id를 찾는다. 이 reader_id를 사용자로 다룬다. 다만 같은 사람도 휴대폰과 PC, 시크릿 창에서는 다른 독자가 되므로 피처는 "브라우저 단위"다. 회원가입이 후속 범위라 로그인 후 기록 합치기는 MVP에서 다루지 않는다.

결정 필요

구독·좋아요를 넣기로 했다. 세호 님 화면 안에는 좋아요가 아직 후속 범위로 적혀 있어 버튼·이벤트(#8)를 다시 맞춰야 하고, 태원 님 쪽에는 subscriptions·likes 테이블과 기사 메타의 publisher_id가 필요하다(#4 #6).

문제·불확실

프론트엔드가 request_id와 position을 모든 노출 이벤트에 실어 보내야 한다. 빠지면 피드백 연결과 위치 편향 보정이 둘 다 안 된다.

문제·불확실

모델이 원하는 이벤트와 수집 쪽이 만들 수 있는 이벤트가 다를 수 있다. 우선순위는 impression, click, read_end, visit 순서로 제안한다.

문제·불확실

학습-서빙 피처 불일치. 학습은 BigQuery SQL로, 서빙은 다른 코드로 피처를 만들면 값이 어긋난다. 학습과 서빙이 같은 피처 테이블을 읽게 한다.

결정 필요

피처 공유 방식(#15). BigQuery 피처 테이블 스키마와 서빙용 피처 파일의 경로·컬럼을 추론 서버 담당과 합의해야 한다.

문제·불확실

Memorystore(Redis)의 용도는 멘토 답을 기다리는 중이다(WBS Q8). 답을 받기 전까지 MVP는 배치 피처 파일로 가고, 실시간 피처가 필요해지면 Redis를 붙인다.

결정 필요

기사 임베딩 담당. 처리·피처·모델 파트의 피처 DAG가 매시 새 기사만 계산하는 안을 추천한다(STEP 3 embed_articles). 임베딩 모델은 모델 쪽이 실험하며 바꾸는 입력이라 같은 파트가 맡는 편이 낫고, 뉴스 쪽은 기사 메타만 정확히 주면 된다. 태원 님 동의가 필요하다.

문제·불확실

새 기사는 최대 1시간 늦게 임베딩이 생긴다. 그동안은 최신순·인기순 후보 생성이 새 기사를 후보에 넣어 준다. 더 빨라야 하면 실행 주기를 10분으로 줄인다.

결정 필요

기사 세부 태그(#18)와 자극도 점수를 기사 메타에 넣을 수 있는지 태원 님과 확인한다.

문제·불확실

단기 관심 피처를 실시간으로 만들 가치가 있는지 아직 모른다. 배치 버전과 비교해 효과가 있을 때만 스트림으로 바꾼다.

DAG 설계 원칙

  • 다시 돌려도 같은 결과: 날짜·시간 파티션 단위로 지우고 다시 쓴다. 같은 시간을 두 번 돌려도 행이 두 배가 되지 않는다.
  • 과거 재처리(backfill): 합성 데이터 180일치를 처음 넣을 때와 로직을 고쳤을 때 날짜 범위를 지정해 다시 돌린다.
  • 파티션과 클러스터링: 모든 테이블을 event_date로 파티션하고 user_id나 article_id로 클러스터링한다. 30일 창 계산이 전체 테이블을 읽지 않게 한다(#22).
  • 로컬 먼저: 로컬 compose(#16)의 Airflow와 폴더형 GCS에서 같은 DAG를 먼저 돌리고, 클라우드로 옮긴다.
  • 품질 검사: 층마다 행 수, 빈 값 비율, 중복 비율을 기록한다. 기준을 넘으면 다음 단계를 멈춘다.

STEP 3+실시간 수집으로 넓힐 때: Pub/Sub

Pub/Sub이 하는 일

GCP가 운영하는 메시지 중개 서비스다. 보내는 쪽(Publisher, 여기서는 로깅 서버)이 토픽에 메시지를 올린다. 받는 쪽(Subscriber)은 그 토픽에 붙인 구독에서 메시지를 받아 처리한 뒤 ack(처리 완료 응답)를 보낸다. 받는 방식은 Subscriber가 가져가는 Pull과 Pub/Sub이 HTTP로 보내 주는 Push 두 가지다.

필요한 이유무슨 뜻인가우리 경우
보내는 쪽이 기다리지 않음로깅 서버는 토픽에 올리기만 하고 바로 다음 요청을 받는다. 저장이 끝날 때까지 기다리지 않는다피드 응답이 저장 속도에 묶이지 않는다
몰려도 버팀클릭이 한꺼번에 쏟아져도 토픽에 쌓아 두고 받는 쪽이 자기 속도로 처리한다가상 독자를 대량으로 돌릴 때 유용하다
받는 쪽이 멈춰도 안 사라짐ack를 받기 전까지 Pub/Sub이 메시지를 보관하고 다시 보낸다저장 프로그램을 재시작해도 이벤트가 빠지지 않는다
여러 곳이 각자 받음구독마다 메시지 사본을 하나씩 받는다원본 보관과 실시간 피처 갱신을 따로 붙이고, 로깅 서버는 고치지 않는다
문제·불확실

Pub/Sub은 "최소 한 번 전달"이다. ack가 정해진 시간(기본 10초) 안에 오지 않으면 같은 메시지를 다시 보내서 중복이 생긴다. 지금 clean 단계의 event_id 중복 제거를 그대로 쓴다. event_id는 클릭 순간에 만들어야 하고, Pub/Sub의 message_id로 대신하면 안 된다.

문제·불확실

메시지 순서는 보장되지 않는다. 도착 순서가 아니라 event_time으로 정렬한다.

결정 필요

도입 시점. 배치 "최근 클릭 5개"와 실시간 버전을 비교해 CTR 차이가 확인될 때만 붙이는 것을 제안한다. 비용과 운영 부담이 늘어나기 때문이다.

문제·불확실

수집 경로를 바꾸면 누락·지연을 다시 검증해야 한다. 가상 독자가 보낸 이벤트 목록과 BigQuery에 도착한 목록을 대조해 누락 수, 중복 수, 도착 지연을 잰다.

최소 데이터 양과 기간(#19). 데이터를 10%, 30%, 100%로 늘려 학습해 보고, 성능이 더 오르지 않는 지점을 최소량으로 잡는 방법을 제안한다.

문제·불확실

가상 독자의 클릭 확률은 우리가 정한 공식이다. 모델은 그 공식을 다시 배우는 것이라, 잘 맞혀도 "연결이 제대로 됐다"는 증거일 뿐이다.

문제·불확실

피드백 루프를 돌리면 모델이 보여 준 기사에만 클릭 기록이 쌓인다. 노출 편향이 생기므로 일정 비율은 무작위나 baseline 추천을 섞어야 한다.

문제·불확실

MIND는 영어 기사이고 연구 목적 라이선스다. 코드 점검과 비교에만 쓰고 서비스 화면에는 쓰지 않는다.

STEP 5학습 데이터 구성

  1. 한 행 = 노출 한 건. 같은 세션에서 클릭이 따랐으면 1, 아니면 0이다.
  2. 시점 기준 피처. 노출 시각 이전 데이터로만 피처를 만든다. 10월 15일 09시 노출에는 feature_date = 10월 14일 스냅샷을 붙인다.
  3. 시간으로 나눠 평가. 무작위로 섞지 않는다. 앞 구간은 학습, 다음 구간은 검증, 마지막 구간은 테스트에 쓴다.
  4. 빼는 데이터. 페르소나 컬럼은 학습에 넣지 않는다. 정제 단계에서 봇으로 표시된 사용자도 빼고, 몇 명을 뺐는지 기록한다.
문제·불확실

데이터 누수. 노출 이후의 클릭이 피처에 섞이면 학습 성능은 높게 나오지만 서비스에서는 맞지 않는다. 조인 날짜 규칙을 테스트로 고정한다.

결정 필요

라벨 기준. 체류 시간이 아주 짧은 클릭을 0으로 볼지 실험으로 정한다.

문제·불확실

클래스 불균형. CTR이 낮으면 0이 1보다 훨씬 많다. 음성 샘플링 비율과 확률 보정 방법이 필요하다.

문제·불확실

위치 편향. 위에 있어서 눌린 효과를 빼야 기사 자체의 매력을 배운다. 학습 때 위치를 피처로 넣고 서빙 때 1번 자리로 고정하는 방법을 쓰지만 효과는 실험해 봐야 안다.

STEP 6후보 생성

전체 기사 중 10~20개로 좁히는 단계다. 여러 방법의 결과를 합쳐서 쓴다. 한 가지만 쓰면 놓치는 기사가 생기기 때문이다.

방법설명장점한계판단
최신순·인기순최근 발행 순, 최근 1시간 클릭 순바로 구현된다, 신규 사용자에게 쓸 수 있다개인화가 없다1차 선택
카테고리 선호 규칙사용자가 많이 본 카테고리의 최신 기사단순하고 설명이 쉽다같은 카테고리 안에서는 구분하지 못한다1차 선택
임베딩 유사도 검색사용자 임베딩과 가까운 기사 임베딩 찾기 (FAISS, ScaNN, Vertex AI Vector Search)새 기사도 바로 후보가 된다임베딩 품질에 좌우된다비교군
Item-based CF함께 클릭된 기사끼리 묶기내용을 몰라도 된다클릭이 쌓이기 전 새 기사는 못 다룬다비교군
ALS 행렬 분해사용자×기사 클릭 행렬을 두 벡터로 분해추천 기본 모델로 널리 쓰인다학습 뒤 나온 기사에는 벡터가 없다비교군
Two-tower사용자 타워와 기사 타워 신경망을 학습해 같은 공간에 놓기 (YouTube DNN 계열)대규모 후보 검색의 표준 구조학습 데이터와 GPU가 더 필요하다확장
GRU4Rec, SASRec클릭 순서를 보고 다음 클릭을 예측하는 세션 모델단기 관심을 잘 잡는다세션 데이터가 충분해야 한다확장
문제·불확실

새 기사 콜드 스타트. 뉴스는 몇 시간 안에 가치가 떨어진다. 클릭 기반 방법(CF, ALS)은 새 기사를 다루지 못하므로 내용 기반 방법이 필요하다.

문제·불확실

신규·익명 사용자 콜드 스타트. 클릭 기록이 없으면 인기순으로 대체한다.

결정 필요

방법별로 후보를 몇 개씩 가져와 합칠지 정해야 한다. 후보가 10~20개뿐이라 이 비율이 결과를 크게 바꾼다.

STEP 7baseline과 CTR 모델 #13

먼저 인기순 baseline으로 피드를 띄우고(중간발표 #25), 그 다음 CTR 모델로 바꾼다. 1차 CTR 모델은 LightGBM이다. 표 형태 피처에 강하고 학습이 몇 분 안에 끝나며, 피처 중요도와 SHAP으로 설명하기 쉽다.

모델설명장점한계판단
인기순 baseline최근 1시간 CTR이나 클릭 수 순서피처 DAG 하나로 바로 된다모두에게 같은 목록1차 선택
로지스틱 회귀피처의 가중합으로 확률 계산가장 설명이 쉽다피처 사이의 상호작용을 못 잡는다비교군
LightGBM결정 트리를 순서대로 쌓는 GBDT. binary 또는 LambdaRank 목적 함수빠르고 정확, SHAP 설명텍스트는 임베딩 피처로 바꿔 넣어야 한다1차 선택
XGBoost, CatBoost다른 GBDT 구현. CatBoost는 범주형 피처 처리가 강하다LightGBM과 바로 비교 가능차이가 크지 않을 수 있다비교군
FM, FFM피처 쌍의 상호작용을 벡터 내적으로 학습희소한 범주형 피처에 강하다구현과 튜닝이 GBDT보다 번거롭다비교군
Wide & Deep, DeepFM, DCN v2기억(wide)과 일반화(deep)를 합친 CTR 예측 신경망산업 CTR 예측의 표준 구조데이터가 적으면 GBDT보다 못할 수 있다확장
DIN후보 기사와 비슷한 과거 클릭에 가중치를 주는 attention 모델관심사가 여럿인 사용자에 강하다구현 난이도가 높다확장
DKN제목의 단어 벡터와 지식 그래프 엔티티 벡터를 함께 쓰는 뉴스 모델엔티티 연결을 활용한다영어 Wikidata 기반이라 한국어에 그대로 쓰기 어렵다보류
NPA, NAML, LSTUR사용자별 attention, 카테고리·본문 결합, 장·단기 관심 분리MIND에서 검증된 뉴스 모델제목 인코더 학습에 GPU가 필요하다확장
NRMS제목 단어끼리, 기사끼리 self-attention으로 기사·사용자 벡터를 만든다MIND 대표 기준선, 구조가 단순하다GBDT 피처와 함께 쓰려면 구조 설계가 필요하다확장
PLM 기반 뉴스 인코더제목 인코더를 BERT 계열 사전학습 모델로 교체MIND 성능이 가장 높은 계열학습·추론 비용이 크다보류
LLM 재랭킹LLM에 사용자 이력과 후보 목록을 주고 순서를 받는다데모 효과가 크고 이유 설명을 받을 수 있다호출당 비용과 지연, 결과가 매번 달라질 수 있다보류
결정 필요

목적 함수. 클릭 여부를 맞히는 binary로 할지, 노출 목록 안의 순서를 맞추는 LambdaRank로 할지 비교해서 고른다.

문제·불확실

딥러닝 모델은 합성 데이터 규모로 충분히 학습되는지 모른다. MIND-small에서 먼저 돌려 보고 GBDT와 차이가 있을 때만 가져온다.

문제·불확실

GPU 비용. 뉴스 전용 딥러닝 모델을 학습하려면 GPU가 필요하다. 크레딧 범위 안에서 가능한지 장주현 님과 확인한다.

문제·불확실

모델 고르기에 시간을 많이 쓰지 말라는 멘토 조언이 있었다. 비교군은 같은 학습 데이터로 한 번씩만 돌리고 피처 개선에 시간을 더 쓴다.

STEP 8후처리 · 탐색

점수 순서를 그대로 보여 주지 않고 규칙으로 다듬는다. 같은 주제만 연달아 나오거나 이미 본 기사가 다시 나오는 것을 막는다.

방법설명판단
규칙 기반이미 클릭한 기사 제거, 같은 카테고리 연속 3개 이하, 최신 기사 1개 이상1차 선택
MMR점수가 높으면서 이미 고른 기사와 덜 비슷한 기사를 하나씩 고른다비교군
DPP목록 전체의 다양성을 확률 모델로 계산해 고른다보류
ε-greedy일정 비율 자리에 무작위 기사를 넣어 새 관심을 탐색한다확장
Thompson sampling, LinUCB불확실한 기사를 더 자주 시험해 보는 밴딧. LinUCB는 Yahoo! 뉴스 추천 연구에서 나왔다확장
결정 필요

다양성과 CTR은 서로 맞바꾸는 관계다. 다양성을 얼마나 줄지, 어떤 지표로 볼지 정해야 한다.

결정 필요

탐색 비율. 노출 편향을 줄이려면 일부 자리는 탐색에 써야 하지만, 그만큼 당장의 CTR은 떨어진다.

STEP 9평가 · 검증 #13 #23

단계무엇을통과 기준
코드 점검MIND-small로 학습·평가 코드를 먼저 돌린다 (recommenders 라이브러리 예제와 비교)AUC가 MIND 논문 기준선과 비슷한 범위
baseline 비교인기순, 최신순, 카테고리 선호 규칙과 비교테스트 구간 CTR·AUC가 baseline보다 높음, 이후 nDCG@K 추가
정답 대조페르소나별로 추천된 카테고리 비율을 페르소나 카드와 비교예: 직장인 그룹 추천에서 경제 비율이 가장 높음

결과는 BigQuery 위 대시보드에서 model_version별, 페르소나별, 위치별 CTR로 본다. 실험 기록은 MLflow 또는 Vertex AI Experiments로 남긴다.

문제·불확실

오프라인 지표가 올라도 온라인 CTR이 함께 오르지 않을 수 있다. 두 숫자를 같이 보여 줘야 한다.

문제·불확실

기록된 로그로 하는 평가는 이전 모델이 보여 준 기사만 평가할 수 있다. 새 모델이 다른 기사를 고르면 정답이 없어 정확한 비교가 어렵다.

결정 필요

A/B 그룹을 나누는 방식. user_id 해시로 고정할지, 실험 기간과 그룹 비율을 어떻게 할지 정한다.

결정 필요

실험 기록 도구로 MLflow를 쓸지 Vertex AI Experiments를 쓸지 정한다.

STEP 10서빙 연결 #14 #20

WBS 문서의 추천대로 1차는 요청 시 점수화다(Q3). 뉴스 WAS와 추론 서버는 따로 두고 HTTP로 주고받는다(Q4). 추론 서버는 세 부분으로 나눈다(Q2 추천안을 나눈 것). 점수화 코드·API·컨테이너 이미지는 윤모가 맡는다. 이 이미지를 GKE에 띄우는 Helm 설정은 장주현 님의 #2 작업이다. 뉴스 WAS에서 추론 서버를 부르고, 실패하면 인기순 피드로 대신하는 부분은 태원 님 쪽이다.

요청 시 점수화 1차 선택미리 계산해 저장 확장
동작독자가 피드를 열면 뉴스 WAS가 후보 10~20개를 추론 서버에 보냄 → 추론 서버가 메모리에 올려 둔 피처 파일과 모델로 점수 → 순서대로 응답배치가 사용자별 추천 목록을 미리 계산해 저장 → 뉴스 WAS가 user_id로 꺼냄 (Redis 필요)
장점구조가 단순하다, 후보가 적어 지연이 작다, 새 기사가 후보에 바로 들어간다응답이 가장 빠르다
단점피처는 배치 주기만큼 늦다, 추론 서버가 떠 있어야 한다저장소와 배치가 더 필요하다, 접속하지 않는 사용자 몫도 계산한다

서빙 런타임 후보

방법설명판단
LightGBM 네이티브학습한 모델 파일을 파이썬에서 그대로 불러 예측1차 선택
ONNX Runtime, Treelite모델을 표준 형식이나 컴파일된 코드로 바꿔 학습 도구와 분리비교군
GKE + FastAPI직접 만든 추론 서버를 Helm으로 배포 (#2)1차 선택
Vertex AI EndpointsGCP가 관리하는 모델 서빙. 서버 관리가 적다비교군
KServe, Triton, TorchServe모델 서빙 전용 서버. 딥러닝 모델일 때 고려확장

모델 파일은 GCS에 버전별 폴더로 올린다. 응답에는 request_id와 model_version을 실어 노출 이벤트로 돌아오게 한다.

결정 필요

요청 시 점수화(#20)는 추천안이다. 추론 서버 코드(#14)는 윤모가 맡기로 했고, 배포·호출 분담은 장주현·태원 님 확인이 필요하다. 그리고 "후보 10~20개 요청 시 점수화로 충분한가"를 10/31에 멘토님께 한 줄 확인한다.

결정 필요

뉴스 WAS ↔ 추론 서버 요청·응답 형식(후보 목록, user_id, 점수, request_id, model_version)을 계약으로 먼저 정해야 둘이 따로 개발할 수 있다.

문제·불확실

피처 파일을 다시 불러오는 시점에 서버가 잠깐 멈추거나 옛 피처를 쓸 수 있다. 새 파일을 다 읽은 뒤에 교체하는 방식으로 만든다.

문제·불확실

학습 도구와 서빙 런타임이 다를 때 어떤 패키징이 적절한지 멘토님 의견을 듣는다.
