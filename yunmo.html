전체 그림

뉴스 WAS가 피드 응답에 넣어 보낸 기사 목록(impression)과, 독자 화면에서 실제로 보인 기사(exposure)·클릭·읽기 기록은 로깅 서버를 거쳐 GCS에 5분 단위로 쌓인다. 피처 DAG가 이것을 BigQuery에서 원본 → 정제 → 집계 → 피처로 바꾸고, 모델도 학습한다. BigQuery는 학습용 오프라인 피처 스토어이고, DAG가 매시 최신 피처를 온라인 피처 스토어인 Valkey(Redis 호환)에 적재한다 (10/31 멘토링 결정). 점선 안의 추론 서버는 GKE 내부망에 있고, 켜질 때 MLflow에서 Production 모델을 메모리로 불러온 뒤, 피드 요청이 올 때마다 Valkey에서 사용자·후보 피처를 조회해 후보 10~20개에 점수를 매긴다. 구독·좋아요(노란 상자)는 누르는 즉시 뉴스 WAS가 Cloud SQL에 저장해 화면에 바로 보이고, 피드 요청 때 구독 언론사 목록을 추론 서버에 함께 넘겨 순서에도 바로 반영한다. 같은 행동은 로깅 서버로도 가서 1시간 뒤 피처가 된다. 학습 결과는 MLflow에 실험 기록(파라미터, AUC)과 모델 버전으로 남기고, 검증을 통과한 버전을 Production으로 올리면 추론 서버가 그 버전을 불러 쓴다. 굵은 파란 테두리가 처리·피처·모델 파트가 만드는 부분이다. 선을 누르면 그 선으로 오가는 데이터가 그림 아래에 나온다. 맨 아래 띠의 Cloud SQL, BigQuery, GCS는 우리 서버가 아니라 구글 데이터센터에서 구글이 운영하는 저장소다. 피처 DAG는 BigQuery에 SQL을 보내기만 하고, 계산과 결과 저장은 BigQuery 안에서 일어난다.

선을 누르면 그 선으로 오가는 데이터가 여기에 나온다. 규약이 있는 선은 필드 표까지 나온다. 번호 배지(①~⑦)는 경계 7곳의 규약이다. 점선은 데이터가 오가지 않는 실행 순서나 확인이다.

굵은 파란 테두리 = 처리·피처·모델 파트가 만드는 것 · 노란 상자 = 구독·좋아요 · 바깥 점선 = 어디서 도는지 (독자 쪽, Cloud Run, GKE, 구글 운영)

관계는 impression ⊇ exposure이다. 응답에 들어간 기사 중 화면까지 내려온 것만 exposure가 된다. 행동 기록은 impression_id 하나로 자기 impression을 가리킨다. 독자·기사·위치는 반환 기록에서 찾으므로 프론트가 보낸 값과 어긋날 일이 없다. 1초가 되기 전에 누른 빠른 클릭은 유효 exposure 없이 article_open만 남는데, 이것도 impression_id로 impression에 붙여 학습 데이터에 넣는다 (규약 ⑤).

이름은 2026-10-31 멘토링 설명을 따른다. 인프레션(impression)은 API 요청으로 내려간 기사 전체이고(예: 20개 요청), 노출(exposure)은 그중 스크롤하며 실제로 화면에 보인 기사다. 11/3 팀 자료에서 이 이름으로 맞췄다.

모든 행동 기록에 공통으로 필요한 필드는 event_id, event_type, event_time, impression_id, page_type이다. 필드 전체는 인터페이스 규약에 있다.

결정 필요

impression을 누가 기록할지. 응답을 만드는 뉴스 WAS(태원 님)가 남기는 안을 제안한다. 추론 서버가 남기면 실패 시 인기순 대체 피드가 빠진다. 기록 위치를 로깅 서버로 보낼지 Cloud SQL에 둘지도 같이 정한다.

결정 필요

구독·좋아요를 넣기로 했다. 세호 님 화면 안에는 좋아요가 아직 후속 범위로 적혀 있어 버튼·이벤트(#8)를 다시 맞춰야 하고, 태원 님 쪽에는 subscriptions·likes 테이블과 기사 메타의 publisher_id가 필요하다(#4 #6).

주의할 것

뉴스 백엔드는 응답마다 반환 기록을 남기고, 프론트엔드는 모든 행동에 impression_id를 실어 보내야 한다. 빠지면 행동이 어느 응답의 몇 번째 칸이었는지 알 수 없어 피드백 연결과 위치 편향 보정이 둘 다 안 된다. 새 탭이나 상세 직접 진입 때 impression_id를 어떻게 복구할지는 팀 자료에서 아직 정하지 않았다.

문제·불확실

모델이 원하는 이벤트와 수집 쪽이 만들 수 있는 이벤트가 다를 수 있다. 우선순위는 impression, exposure, article_open, like 순서로 제안한다.

주의할 것

학습-서빙 피처 불일치. 학습은 BigQuery SQL로, 서빙은 다른 코드로 피처를 만들면 값이 어긋난다. 학습과 서빙이 같은 피처 테이블을 읽게 한다. Valkey에는 BigQuery feat 테이블 값을 계산 없이 그대로 복사한다.

결정 필요

피처 공유 방식(#15). BigQuery 피처 테이블 스키마와 Valkey 키 형식(예: rf:{ver}:{reader_id}, af:{ver}:{article_id} 해시, 규약 ⑥)·필드 이름을 추론 서버 담당과 합의해야 한다.

주의할 것

온라인 피처 스토어는 Valkey로 정했다 (10/31 멘토링 결정). Valkey가 멈추면 추론 서버가 피처를 못 읽으므로 뉴스 WAS가 인기순 대체 피드로 넘어가야 한다. 매시 적재한 값은 GCS에도 스냅샷으로 남겨, Valkey를 다시 띄울 때 그 파일에서 다시 채운다.

문제·불확실

새 기사는 최대 1시간 늦게 임베딩이 생긴다. 그동안은 최신순·인기순 후보 생성이 새 기사를 후보에 넣어 준다. 더 빨라야 하면 실행 주기를 10분으로 줄인다.

결정 필요

기사 세부 태그(#18)와 자극도 점수를 기사 메타에 넣을 수 있는지 태원 님과 확인한다.

문제·불확실

단기 관심 피처를 실시간으로 만들 가치가 있는지 아직 모른다. 배치 버전과 비교해 효과가 있을 때만 스트림으로 바꾼다.

Pub/Sub이 하는 일

GCP가 운영하는 메시지 중개 서비스다. 보내는 쪽(Publisher, 여기서는 로깅 서버)이 토픽에 메시지를 올린다. 받는 쪽(Subscriber)은 그 토픽에 붙인 구독에서 메시지를 받아 처리한 뒤 ack(처리 완료 응답)를 보낸다. 받는 방식은 Subscriber가 가져가는 Pull과 Pub/Sub이 HTTP로 보내 주는 Push 두 가지다.

필요한 이유무슨 뜻인가우리 경우
보내는 쪽이 기다리지 않음로깅 서버는 토픽에 올리기만 하고 바로 다음 요청을 받는다. 저장이 끝날 때까지 기다리지 않는다피드 응답이 저장 속도에 묶이지 않는다
몰려도 버팀클릭이 한꺼번에 쏟아져도 토픽에 쌓아 두고 받는 쪽이 자기 속도로 처리한다가상 독자를 대량으로 돌릴 때 유용하다
받는 쪽이 멈춰도 안 사라짐ack를 받기 전까지 Pub/Sub이 메시지를 보관하고 다시 보낸다저장 프로그램을 재시작해도 이벤트가 빠지지 않는다
여러 곳이 각자 받음구독마다 메시지 사본을 하나씩 받는다원본 보관과 실시간 피처 갱신을 따로 붙이고, 로깅 서버는 고치지 않는다
주의할 것

Pub/Sub은 "최소 한 번 전달"이다. ack가 정해진 시간(기본 10초) 안에 오지 않으면 같은 메시지를 다시 보내서 중복이 생긴다. 지금 clean 단계의 event_id 중복 제거를 그대로 쓴다. event_id는 클릭 순간에 만들어야 하고, Pub/Sub의 message_id로 대신하면 안 된다.

주의할 것

메시지 순서는 보장되지 않는다. 도착 순서가 아니라 event_time으로 정렬한다.

결정 필요

도입 시점. 배치 "최근 클릭 5개"와 실시간 버전을 비교해 CTR 차이가 확인될 때만 붙이는 것을 제안한다. 비용과 운영 부담이 늘어나기 때문이다.

문제·불확실

수집 경로를 바꾸면 누락·지연을 다시 검증해야 한다. 가상 독자가 보낸 이벤트 목록과 BigQuery에 도착한 목록을 대조해 누락 수, 중복 수, 도착 지연을 잰다.

  1. 한 행 = 유효 exposure가 있는 impression 한 건. 같은 impression_id에 exposure 구간이 여러 개여도 한 행이다. 30분 안에 article_open이 따랐으면 1, 아니면 0이다. 유효 exposure 없이 눌린 빠른 클릭도 그 impression으로 행을 만들어 1로 넣는다. 화면에 안 보인 impression은 0으로 넣지 않는다(못 본 것이지 싫은 것이 아니므로). 표는 규약 ⑤의 train.samples 행 규칙.
  2. 시점 기준 피처 (포인트 인타임 조인). 노출 시각 이전 데이터로만 피처를 만든다. 멘토님이 실시간 추천에서 가장 중요하다고 강조한 규칙이다. 10월 15일 09시 노출에는 feature_date = 10월 14일 스냅샷을 붙인다.
  3. 시간으로 나눠 평가. 무작위로 섞지 않는다. 앞 구간은 학습, 다음 구간은 검증, 마지막 구간은 테스트에 쓴다.
  4. 빼는 데이터. 페르소나 컬럼은 학습에 넣지 않는다. 정제 단계에서 봇으로 표시된 사용자도 빼고, 몇 명을 뺐는지 기록한다.
주의할 것

데이터 누수. 노출 이후의 클릭이 피처에 섞이면 학습 성능은 높게 나오지만 서비스에서는 맞지 않는다. 조인 날짜 규칙을 테스트로 고정한다.

결정 필요

주의할 것

문제·불확실

결정 필요

요청 시 점수화(#20)는 추천안이다. 추론 서버 코드(#14)는 윤모가 맡기로 했고, 배포·호출 분담은 장주현·태원 님 확인이 필요하다. 요청 시 점수화 자체는 10/31 멘토링에서 확정됐다.

결정 필요

뉴스 WAS ↔ 추론 서버 요청·응답 형식은 인터페이스 규약 ②에 초안을 적었다. 태원 님이 확인하면 둘이 따로 개발할 수 있다.

주의할 것

새 Production 모델은 서버를 하나씩 새로 띄워(롤링 교체) 불러오게 한다. 한꺼번에 재시작하면 그동안 피드가 인기순으로만 나간다.
