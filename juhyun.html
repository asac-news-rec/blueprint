청사진 정리 (10/28 멘토 요청 → 10/30 13시 발표 대비)

이 파일은 청사진 한 주제만 담는다. 다른 주제(역할, 인프라 비교, 발표 피드백 등)는 각자의 파일에 있다.

작성: 2026-10-30 / 대상: 장주현 / 근거 표기: [멘토] 10/28 Gemini 스크립트·회의록, [팀] 10/29 팀 회의 메모, [제안] 제가 제안한 것(확정 아님), [일반] 일반 지식(이 프로젝트에서 확인한 것 아님).

0. 급할 때 이것만 (30초)

  1. 청사진 = 데이터가 한 바퀴 도는 큰 그림 한 장. 화면 → 백엔드 → 수집 → 배치 → 피처 → (거꾸로) "그럼 처음에 어떤 행동을 모아야 하나". [멘토]
  2. 한 번에 깔끔하지 않아도 된다. AI(에이전트)와 같이 정리해 오면 멘토가 해석해 준다. 금요일 팀이 합치고, 토요일 10시 멘토가 본다. [멘토]
  3. 인프라 초안은 멘토 숙제가 아니다. 우리가 덧붙인 몫이다. 장주현은 "그림의 각 상자가 어디서 돌고 어디에 저장되나"를 얹은 인프라 지도 1장을 들고 간다. [제안]
  4. 인프라 지도 한 줄: 화면(정적 파일) → 백엔드(Cloud Run 또는 GKE) → 로깅 서버 → GCS(5분 폴더) → Airflow(GKE)가 BigQuery에 정리 → 피처 → 추론 서버(GKE 별도) → 다시 화면. DB는 Cloud SQL, Redis는 용도 미정. 멘토 방침은 확정, 나머지는 제안.
  5. 발표 때 한마디: "저는 이 흐름의 각 상자가 어디에서 돌아가는지와, 11/5 전에 모두가 같은 환경에서 시작하도록 로컬 compose를 만드는 것을 맡습니다."
  6. 받을 것: 태원에게 기사 컬럼, 세호에게 이벤트 필드와 하루 이벤트 수, 윤모에게 피처와 배치 주기.
  7. 그림으로 보려면: 8절(질문 풀이)과 1부 청사진 정리. 인프라 지도는 2부 인프라 구성도.

2-1. 멘토 청사진 부분

(2) 유저 액션을 클릭만 하면 MVP가 되나? 나중에 추가할 수 있나?

  • 된다. 단 "클릭"만으로는 모자라고 "노출"이 같이 필요하다. [일반] CTR은 클릭 수 ÷ 노출 수다. 기사 10개를 보여줬는데 2개를 눌렀다면 CTR 20%인데, "보여준 10개"를 기록하지 않으면 분모를 모른다. 그래서 MVP 최소 이벤트는 ① 노출(피드에 이 기사가 보였다) ② 클릭 두 가지가 안전하다. (태원은 "행동 데이터는 클릭 기반" [팀]이라고 했다. 노출을 포함한다는 뜻인지는 팀이 확인할 항목.)
  • 나중에 추가 가능한가: 가능하다. 이벤트에 event_type 칸을 두고(예: impression, click, dwell, like), 원본은 GCS에 그대로 쌓아 두면 새 이벤트가 생겨도 과거 데이터를 다시 처리할 수 있다. 처음부터 schema_version 칸도 넣어 두면 더 안전하다. [제안]
  • 비유: 설문조사에서 "누른 사람 수"만 세면 안 되고 "설문을 본 사람 수"도 세어야 비율이 나온다.

(2) FE 수집 스크립트는 어떤 게 있어? [일반]

방식쉬운 설명우리에게
직접 작성한 JS클릭하면 "이 기사 클릭됨"을 서버로 보내는 짧은 코드추천. AI가 생성하기 쉽고 로깅 서버와 직접 맞출 수 있다
노출 감지(IntersectionObserver)기사 카드가 화면에 절반 이상 보이면 "노출됨"을 기록노출 이벤트를 만들 때 쓴다
전송용 sendBeacon페이지를 닫는 순간에도 안전하게 전송이탈·체류 시간 보낼 때 유용
외부 도구(Google Analytics, GTM, Snowplow 등)이미 만들어진 수집 서비스우리는 로깅 서버를 직접 만들 계획이라 MVP엔 과함

(3) 로깅 서버는 "뉴스 피드 웹페이지에서 모은 유저 행동 로그를 관리하는 서버"가 맞나?

  • 거의 맞다. 정확히는 브라우저가 보낸 행동 기록을 받아서 파일로 쌓아 두는 서버다. "관리"라고 하면 분석까지 들리는데, 분석은 뒤의 배치(Airflow/BigQuery)가 한다. 로깅 서버는 받아서 저장까지만 한다.
  • 비유: 우체통과 서기. 편지를 받아 날짜별 상자에 넣을 뿐, 내용을 해석하지는 않는다.

(3) 로깅 서버를 "따로 만든다"는 무슨 뜻?

  • 뉴스 백엔드(기사를 내려주는 서버)와 별개 프로그램으로 둔다는 뜻이다. 한 서버가 둘 다 하면 로그가 폭주할 때 기사 화면도 느려진다. 멘토는 "제 생각에는 따로 만드는 게 나은 것 같다"고 했고 "백엔드가 쏴줘도 된다"고도 열어 뒀다. [멘토]
  • 비유: 식당의 주문 받는 홀(백엔드)과 방문객 기록실(로깅 서버)을 나누는 것. 기록실이 붐벼도 홀은 안 느려진다.
  • 장점: 서로 영향이 적음, 따로 늘릴 수 있음. 단점: 관리할 서버가 하나 더. [일반]

(3) GCS에 파티션으로 쌓는다는 건 예를 들면?

  • 파일을 시간대별 폴더에 나눠 넣는 것. 5분 단위 예: 
gs://news-raw/events/dt=2026-11-10/hh=09/mm=05/part-0001.jsonl    ← 09:05~09:09의 이벤트
gs://news-raw/events/dt=2026-11-10/hh=09/mm=05/_SUCCESS            ← "이 5분 폴더는 다 들어왔다" 표시
gs://news-raw/events/dt=2026-11-10/hh=09/mm=10/part-0001.jsonl    ← 09:10~09:14
  • 왜: 배치가 "이 5분 구간만" 읽고, 실패하면 그 구간만 다시 한다. 폴더가 짧을수록 파일 수가 늘어난다. 멘토는 5분을 권했다("한 시간은 너무 길다"). [멘토, 스크립트 00:40~00:41]

(4) '쿠키에 FE 스크립트로 발급'은 구체적으로? [일반]

  1. 사용자가 사이트에 처음 들어오면, FE 스크립트가 쿠키에 user_id가 있나 확인한다.
  2. 없으면 무작위 번호(UUID)를 새로 만들어 쿠키에 저장한다(예: 유효기간 1년).
  3. 이후 모든 이벤트와 백엔드 요청에 그 번호를 같이 보낸다. 
let uid = getCookie('uid');
if (!uid) { uid = crypto.randomUUID(); setCookie('uid', uid, 365); }
  • 장점: 회원가입 없이 "같은 사람"을 구분. 단점: 쿠키를 지우면 새 사람이 된다. 우리의 가상 독자(합성 데이터)는 쿠키 대신 페르소나 ID를 user_id로 직접 쓴다. [제안]

(5) '클릭 모델 피처 목록(클릭한 기사와 유사한 임베딩 포함)'이 무슨 말?

  • 피처 = 모델이 "이 사람이 이 기사를 누를까?"를 맞힐 때 쓰는 재료 숫자들. 임베딩 = 기사 글을 숫자 목록(벡터)으로 바꾼 것. 비슷한 글은 숫자도 가깝다. [일반]
  • 예: 반도체 기사 A [0.8, 0.1, 0.3…], 반도체 기사 B [0.7, 0.2, 0.3…] → 가깝다(유사도 0.9). 스포츠 기사 C [0.1, 0.9, 0.0…] → 멀다(유사도 0.1).
  • 피처 예: "이 사람이 최근 클릭한 기사 5개의 평균 벡터와, 지금 후보 기사의 유사도" → 반도체를 자주 본 사람에게 반도체 기사 점수가 올라간다. [멘토: 클릭한 기사와 유사한 임베딩 피처 가능]

(5) '거꾸로 필요한 이벤트를 되짚는다'는 어떤 과정?

  • 모델 재료(피처)에서 시작해 "그걸 만들려면 무슨 기록이 있어야 하지?"를 끝에서 앞으로 거슬러 올라가는 것.
만들고 싶은 피처필요한 원재료그러려면 수집해야 할 이벤트/필드
최근 7일 카테고리별 클릭 비율누가 어떤 카테고리를 눌렀나 + 몇 번 봤나click, impression, user_id, article_id, 기사의 카테고리, timestamp
기사별 최근 CTR기사별 노출 수와 클릭 수impression, click, article_id
지금 시간대접속 시각timestamp
클릭 기사와의 유사도클릭한 기사 id, 기사 본문(임베딩)click의 article_id, 기사 본문
피드 내 위치 효과몇 번째에 보였나position
  • 표의 오른쪽 열이 FE 수집 스크립트가 보내야 할 목록이 된다. 빠진 칸이 있으면 이벤트를 추가한다.

(6) '합치기'가 무슨 말? 1~5를 하나로 합치라는 뜻?

  • 맞다. 1~5를 각각 따로 쓰지 말고, 같은 데이터가 이름·형식이 바뀌지 않고 끝까지 이어지는지 한 장에서 확인하라는 뜻이다. 예: article_id가 화면 응답에서도, 이벤트에서도, 피처 계산에서도 같은 이름·같은 형식인가. "무작정 조립 금지"는 각자 만든 걸 안 맞춰 보고 붙이지 말라는 경고다.

(6) '에이전트와 같이 하라'는 무슨 말?

  • ChatGPT·Claude 같은 AI에게 물어 가며 초안을 만들라는 뜻이다. 멘토는 "한 번에 깔끔하게 못 그릴 것이다. 에이전트에게 정리하라고 하면 정리해 주고, 해석은 내가 한다"고 했다. [멘토, 스크립트 00:43] 즉 초안을 AI가 쓰게 하되, 우리가 이해하고 설명할 수 있어야 한다(멘토는 이해 확인 장치도 둘 것이라고 함).
  • 질문 예: "뉴스 피드 CTR 예측 모델에 보통 들어가는 피처를 알려줘. 각 피처를 만들려면 어떤 이벤트가 필요한지 표로."

(마지막) 위에서 구체적으로 생각한 내용을 청사진으로 들고 가면 되나?

  • 네, 그렇게 가져가면 된다. 단 청사진은 정답이 아니라 "현재 우리 생각을 이어서 그린 초안"이다. 장주현이 들고 갈 것은 ① 이 흐름을 이해했다는 한 줄 요약 ② 인프라 지도 1장 ③ 받을 것 표 ④ 미정 질문 3개. 팀 전체 청사진은 4명 자료를 합친 것이다.

2-2. 인프라 지도 부분

1. 화면(정적 빌드)이 뭐지?

  • 정적 = 서버가 그때그때 계산하지 않는, 이미 완성된 파일(HTML/CSS/JS)이라는 뜻. 빌드 = 개발용 소스를 배포용 파일로 묶는 작업(예: npm run build가 dist/ 폴더를 만든다).
  • 비유: 주문받고 만드는 즉석요리(서버가 화면 생성)가 아니라, 미리 만들어 둔 도시락(파일을 그대로 전달). 기사 내용은 화면이 열릴 때 백엔드에서 받아 채운다.
  • 장점: 서버를 따로 안 켜도 되고 GCS에 올려 두기만 하면 된다. 팀 frontend 프로토타입이 이 방식(dist/)이다(사실). 호스팅 방식은 제안.

2. 백엔드(Cloud Run 또는 GKE)가 무슨 말?

  • 백엔드 = 기사 목록·상세를 DB에서 꺼내 화면에 주는 서버 프로그램. "어디서 실행시킬까"의 두 후보라는 뜻이다.
Cloud RunGKE
한 줄컨테이너를 올리면 알아서 실행, 요청이 없으면 0으로 줄어듦쿠버네티스 클러스터 위에서 직접 운영
장점관리 쉬움, 안 쓰면 비용 낮음같은 곳에 Airflow·추론 서버가 이미 있음, 쿠버 경험
단점다른 서비스(GKE)와 연결 설계가 더 필요클러스터를 켜 두는 만큼 비용, 설정 복잡
근거멘토: "백엔드는 Cloud Run이 편하다"멘토: "가능하면 쿠버 환경을 경험"
  • 아직 미정이다. 장주현이 Q4에서 고른다(청사진 질문형 파일 참고).

3. 'Airflow on GKE → BigQuery'에서 Airflow는 뭘 하고, BigQuery에는 뭘 쌓나?

  • Airflow = 정해진 시각에 작업을 순서대로 자동 실행하는 스케줄러. 실패하면 재시도하고 어디서 멈췄는지 보여 준다.
  • 예 (5분마다 또는 매일): ① GCS의 해당 폴더에 _SUCCESS가 생겼나 확인 → ② 이벤트 정제(중복 event_id 제거, 필수 값 비었으면 오류 보관) → ③ BigQuery에 적재 → ④ 집계(사용자×카테고리 클릭 비율 등) → ⑤ 피처 계산.
  • BigQuery에 쌓는 것 (테이블 이름은 제안):
구분내용메달리온 이름
정제 이벤트중복·불량을 걸러 낸 노출/클릭 기록실버
집계·피처사용자별 카테고리 클릭 비율, 기사별 CTR 등골드
학습용 데이터"그 시점에 알던 피처 + 정답(클릭했나)"골드
  • 원본(GCS)은 브론즈. BigQuery는 "쌓인 걸 한꺼번에 계산하는 창고"다. 학습 레포 airflow-medallion-rag의 DAG 모양과 같다(Sensor → 검사 → 병렬 → 합치기).

4. 'Cloud SQL'은 뭐고 왜 필요해?

  • Cloud SQL = 구글이 설치·백업을 대신해 주는 관계형 DB(Postgres). 기사·구독을 한 건씩 빠르게 읽고 쓰는 곳이다.
  • 왜 필요: 뉴스 백엔드가 기사 한 건을 보여줄 때마다 BigQuery에 물으면 느리고 비싸다. BigQuery는 "대량 집계용", Cloud SQL은 "건별 서비스용"이다. 멘토가 핵심 제품에 "SQL 스토리지"로 꼽았고, 매니지드 대신 직접 띄우는 쪽을 권하되 RDB까지는 매니지드 허용이라는 타협이 있었다. [멘토]
  • 비유: 계산대 옆 서랍(Cloud SQL)과 지하 창고(BigQuery).

5. Redis는 어떤 활용처가 있고 어떻게 쓰나? [일반]

  • Redis = 메모리에 "키 → 값"을 두는 초고속 저장소.
활용설명예
캐시자주 찾는 결과를 메모리에 잠시 보관오늘의 인기 기사 목록
온라인 피처사용자별 최신 피처를 즉시 읽기user:u123:cat_ratio → {"경제":0.7}
카운터·순위실시간으로 숫자를 올림기사별 클릭 수 +1
제한·세션중복 요청 막기, 임시 상태같은 클릭 연타 방지
  • 우리는: 멘토가 핵심 제품에 Memorystore를 넣었지만 용도 설명이 없었다. 그래서 10/31 멘토 질문이고, 그때까지 MVP는 "자리만" 두는 게 안전하다. [멘토 + 제안] Valkey는 Redis에서 갈라진 오픈소스로 사용법이 거의 같다.

6. 로컬 compose 계획은 어떻게 세우나?

  • compose = docker compose up 한 줄로 여러 프로그램을 내 컴퓨터에 함께 띄우는 파일. 클라우드 없이 팀원 모두가 같은 환경에서 개발하게 한다.
  • 무엇을 넣을지 목록: Postgres, Redis, Airflow(+메타 DB), 폴더형 GCS(그냥 로컬 폴더), (나중에) 로깅 서버·백엔드 자리.
  • 각자 서비스는 Dockerfile이 생기면 한 줄씩 추가.
  • .env.example에 포트·환경변수 이름 합의(비밀값은 올리지 않음).
  • 샘플 데이터(기사 수십 개, 이벤트 수백 개)를 같이 넣기.
  • README에 "docker compose up 후 이 주소로 확인".
  • 일정: 범위 합의 11/3, 팀 배포 11/5 전. [제안, WBS 근거]
  • 참고 자료: 학습 레포 airflow-medallion-rag/docker-compose.yaml. BigQuery는 로컬 대체가 약해서 샘플 SQL 파일로 두고 클라우드에서 검증한다.

6. 'CTR 평가'가 뭐지?

  • CTR(Click-Through Rate, 클릭률) = 클릭 수 ÷ 노출 수. 예: 100번 보여줬는데 8번 클릭 → 8%.
  • 평가 = 개인화 추천이 기본 방식(예: 인기순)보다 CTR이 높은지 비교하는 것. 멘토는 "일단 CTR"로 시작하라고 했고 nDCG@K는 후순위다. [멘토]

7. '엔진 성과'는 모델의 성능을 뜻하는 게 맞아?

  • 거의 맞다. 태원이 말한 "엔진 성과가 홈페이지 편의성보다 우선" [팀]에서 엔진은 추천 엔진(모델 + 점수를 계산해 주는 서빙)으로 읽힌다(추정). 모델이 얼마나 잘 맞히는지(정확도)와 서비스에서 제대로 돌아가는지(응답 속도 등)를 포함할 수 있다. 정확한 뜻은 태원에게 확인.

8. 엔진 성과도 정량적으로 나와야 하고, 어떻게 확인하나? → 맞다. 숫자로 나와야 한다. 방법 두 가지 [일반]:

방식하는 일예
오프라인 평가과거 데이터를 시간 순서로 나눠 앞쪽으로 학습, 뒤쪽으로 시험인기순 CTR 8% vs 모델 추천 CTR 11% (예시 숫자)
온라인 평가가상 독자에게 두 방식을 섞어 보여주고 CTR 비교(A/B)인기순 피드 vs 개인화 피드
  • 모델 자체 지표로는 AUC, 로그 손실 등이 있다(전문 용어는 나중에 필요할 때). 한계: 가상 독자는 합성 데이터라 숫자가 실제 사용자 결과를 보장하지 않는다. 그래서 발표 때 "이 기준으로 비교했다, 한계는 이렇다"까지 말한다.

8-1. [청사진 핵심만] 질문 1~8

1. "이벤트에 event_type 칸"이 무슨 뜻인가?

  • 이벤트 = 사용자 행동 1건을 적은 한 줄 기록(JSON). 노출·클릭·체류가 전부 같은 모양이고, "무슨 행동인지"만 event_type 칸에 적는다.
  • 택배 송장에 "종류" 칸이 있는 것과 같다. 종류마다 입구(서버)와 파일을 따로 만들지 않고, 한 통로로 받아 나중에 종류별로 가른다.
  • 이득: 나중에 "좋아요"가 추가돼도 event_type: "like"만 새로 쓰면 된다. [제안]

2. "노출 기록"은 피드 한 화면에 기사 몇 건이 보였는지를 적는 건가? CTR은 "몇 건 중 몇 건 눌렀나"인가?

  • 둘 다 맞다. 피드에 기사 10건이 보였으면 노출 10건(기사마다 1줄, 또는 화면 1줄에 기사 번호 배열), 그중 2건을 눌렀으면 클릭 2건이다.
  • CTR = 클릭 수 ÷ 노출 수 = 2 ÷ 10 = 20%. 멘토가 CTR을 1순위 지표로 말했다. [멘토]
  • 노출을 언제 기록하나(응답을 보낸 시점 vs 화면에 실제로 보인 시점)는 팀이 정할 일. MVP는 "응답을 보낸 시점"이 가장 단순하다. [제안]

3. "노출 포함 여부"는 무슨 뜻인가?

  • "수집하는 이벤트에 노출을 넣을 것인가 말 것인가"를 팀이 정하라는 뜻이다.
  • 안 넣으면: 클릭 수는 알지만 분모(노출 수)를 몰라 CTR을 못 구한다. 학습 데이터에 "안 눌린 사례(0)"도 만들 수 없다(8-5 참고).
  • 넣으면: 로그 양이 클릭의 약 10배로 늘지만 하루 수천 건 수준이면 문제가 없다(8-2 계산). 그래서 "넣자"가 제 제안. 팀 확인 필요.

4. "분석은 뒤의 배치가 합니다"는?

  • 로깅 서버는 받아서 파일로 저장만 한다. 클릭률 계산·집계 같은 분석은 정해진 시간에 도는 Airflow 배치가 파일을 읽어서 BigQuery에서 한다.
  • 편의점으로 비유: 계산대는 영수증을 쌓기만 하고(로깅 서버), 마감 정산은 점장이 밤에 한다(배치). 계산대가 정산까지 하면 손님 줄이 길어진다. [일반]

5. "_SUCCESS"는 왜 그런 이름인가? 로그 적재가 성공했다는 뜻인가?

  • 폴더가 아니라 내용이 비어 있는 파일이다. 이름은 Hadoop/Spark 세계의 관례("이 작업이 끝까지 성공했다"는 표시 파일)를 따온 것이다. [일반]
  • 의미: "이 5분 폴더는 파일 쓰기가 완전히 끝났다." 서버가 다 쓰고 나서 마지막에 만든다. 배치는 _SUCCESS가 있는 폴더만 읽어서, 쓰다 만 반쪽 파일을 읽는 사고를 막는다.
  • 우리가 이 관례를 쓸지는 팀 결정이다(제안). 그림은 8-3.

6. "거꾸로 되짚기" (다시 질문하신다고 해서 짧은 한 사슬 예시만)

  • 모델이 쓰고 싶은 피처: "독자의 최근 7일 IT 기사 클릭률"
  • 그 피처를 만들려면 필요한 원료: 독자별·카테고리별 노출 수와 클릭 수
  • 그 원료가 로그에 있으려면 이벤트에 필요한 칸: event_type(노출/클릭), user_id, article_id, 기사 카테고리(또는 article_id로 조회), ts
  • 즉 "피처 → 원료 → 이벤트 칸" 순서로 거꾸로 걸어 내려가 수집할 이벤트 목록을 확정하는 방법이다. [멘토 숙제 5번]

7. "Cloud Run은 올리면 알아서 실행"에서 어디에 올린다는 건가?

  • 올리는 것 = 프로그램을 담은 컨테이너 이미지. 올리는 곳 = Artifact Registry(이미지 창고).
  • 순서: ① Dockerfile로 이미지를 만든다 → ② Artifact Registry에 push → ③ gcloud run deploy --image <이미지>(또는 Terraform의 Cloud Run 리소스) → ④ 주소(URL)가 생기고 요청이 오면 켜지고, 요청이 없으면 0개로 줄어든다.
  • GKE는 같은 이미지를 K8s 설정 파일(yaml/Helm)로 띄운다는 점만 다르다. [일반]

8. Redis를 쓰는 3가지 (전혀 이해 못 했다고 하신 부분)

  • Redis = 메모리 속 "키 → 값" 사전. DB보다 훨씬 빠르지만 용량이 작고 날아갈 수 있다. [일반]
  • ① 캐시: 같은 질문의 답을 기억. 인기 기사 10건을 매번 DB에서 뽑지 않고 메모리에서 바로 답한다.
  • ② 온라인 피처: 추천 요청 순간에 필요한 값을 즉시 읽기. "민수의 최근 클릭 5건"을 BigQuery에서 읽으면 느리니, 배치가 만든 값을 Redis에 복사해 둔다.
  • ③ 카운터: 기사별 오늘 클릭 수를 클릭이 올 때마다 +1.
  • 중요: 멘토가 Memorystore를 말한 이유는 설명되지 않았다. 위 3가지는 일반 용도이고, 우리가 어느 용도로 쓰는지는 10/31에 멘토에게 묻는다. MVP는 Redis 없이 Cloud SQL로도 가능하다. [일반 + 미확인]

8-2. [0절 "받을 것"] 질문

"받을 것 중 기사 컬럼"은 기사 테이블의 컬럼 목록인가? → 네.

  • 기사 테이블(Cloud SQL)에 어떤 칸(컬럼)이 있는지 기사 담당에게 받으라는 뜻이다. 세호 님이 만든 프론트 프로토타입에는 이미 id, title, summary, category, publishedAt, body, art가 있다(팀 레포 frontend). 이것을 출발점으로 확인하면 된다. [팀 레포]
  • 인프라 담당(나)이 이걸 받는 이유: DB 테이블을 만들려면 칸이 필요하다.

"이벤트 필드"와 "하루 이벤트 수"는?

  • 이벤트 필드 = 이벤트 한 줄에 들어가는 칸(8-1 그림의 event_type, user_id, article_id, ts …).
  • 하루 이벤트 수 = 하루에 기록이 몇 줄 쌓이는지 추정한 값. 저장 용량·배치 시간·"Pub/Sub가 필요한가"를 판단하는 근거다.
  • 계산 예(가정): 독자 100명 × 하루 5번 접속 × 한 번에 노출 10건 = 노출 5,000줄. 클릭률 10%면 클릭 500줄. 합계 약 5,500줄/일. 한 줄 300바이트면 하루 약 1.6MB로 아주 작다. 그래서 MVP는 "파일로 바로 저장"으로 충분하다는 멘토 방향과 맞는다. [제안, 숫자는 가정]

어떤 피처를 쓸지 정하는 건 우리의 몫인가? → 네, 팀 몫이다.

  • 멘토 숙제 5번이 "피처 목록을 쓰고, 거꾸로 이벤트를 도출"하는 것이다. 초안은 처리·추천 담당이 쓰는 게 자연스럽다(담당은 추정). 인프라 담당은 그 피처를 어디에 저장하고 어떻게 서빙하는지(BigQuery, 필요하면 Redis)를 맞춘다. [멘토 + 추정]

8-3. [(3) GCS 파티션] 질문

_SUCCESS는 폴더인가, 다 들어왔다는 표시인가? → 폴더가 아니라, 다 들어왔다는 표시용 빈 파일이다. 그림으로:

"폴더가 짧을수록 파일 수가 늘어난다"는?

  • 폴더 하나에 담는 시간 길이가 짧을수록(5분 < 1시간) 하루에 폴더·파일이 많아지고 하나하나는 작아진다는 뜻이다. 5분 단위는 하루 288개, 1시간 단위는 24개 폴더.
  • 5분: 실패해도 그 5분만 다시 처리하고 반영이 빠르다. 대신 작은 파일이 많다.
  • 1시간: 파일이 적고 관리가 쉽지만 실패하면 1시간치를 다시 하고 반영이 늦다. 멘토는 "한 시간은 너무 길다"고 했다. [멘토]
  • 우리는 하루 수천 줄이라 파일이 작아도 문제가 없다. 큰 서비스에서만 "작은 파일이 너무 많은" 문제가 생긴다. [일반]

8-4. [(5) 거꾸로 부분 + 읽기 불편]

표가 VS Code에서 줄글로 보이는 문제

  • 원인: 마크다운 파일을 편집기(소스) 화면으로 열어서 표가 | a | b | 글자 그대로 보인다. 표 자체가 깨진 것이 아니다.
  • 해결 1: 파일을 연 채 Ctrl+Shift+V(Mac Cmd+Shift+V) 또는 오른쪽 위 "미리보기" 아이콘 → 표와 그림이 그려진다.
  • 해결 2: 같은 이름의 .html 파일을 브라우저로 연다(청사진_정리.html).
  • 앞으로 새로 쓰는 내용은 표를 줄이고 목록 위주로 쓰겠다.

GCS에서도 S3처럼 메달리온(브론즈/실버/골드) 폴더로 정제 데이터를 정리할까?

  • 가능하다. GCS의 폴더는 이름 앞부분(접두어)일 뿐이라 bronze/ silver/ gold/로 나눠도 된다. [일반]
  • 다만 이번 방향(멘토: 배치는 BigQuery)에서는 이렇게 나누는 것이 더 단순하다. [제안]
    • 브론즈(원본) = GCS raw (events/dt=/hh=/mm=/)
    • 실버(정제) = BigQuery clean 데이터셋
    • 골드(피처·집계) = BigQuery feature 데이터셋
  • 학습용 파일(parquet 등)을 따로 내보낼 때만 GCS에 gold/ 폴더를 추가하면 된다. 어디까지 하느냐는 팀·멘토 확인 사항.

8-5. [4. 피처 목록] "한 줄이 (사용자, 기사, 시점) 1건이고 마지막 칸이 정답"?

  • 모델 학습용 표의 한 줄 = "그 독자에게 그 기사가 그 시점에 노출된 1번의 사례"이다. 앞쪽 칸은 사용자·기사·시점을 설명하는 피처이고, 마지막 칸 clicked가 정답(눌렀으면 1, 안 눌렀으면 0)이다.
  • 예: 민수에게 기사 42가 09:05에 보였고 눌렀다 → 1. 같은 민수에게 기사 17도 보였지만 안 눌렀다 → 0.
  • 이 때문에 노출 이벤트가 꼭 필요하다. 클릭한 줄(1)만 있으면 "무엇이 안 눌리는지"를 배울 수 없다.

8-6. [인프라] 직접 방식과 매니지드 방식은 실행하면 어떤 차이인가?

  • 같은 Redis를 두 방식으로 띄운다고 하자(그림).
  • 매니지드(Memorystore): Terraform에 google_redis_instance 블록 한 개 → apply → 몇 분 뒤 주소가 나오면 접속만 하면 된다. 패치·백업·장애 교체는 구글이 한다. 켜 두는 동안 고정 요금.
  • 직접(GKE에 Valkey): helm install(또는 Terraform helm_release) → Pod가 뜸 → 클러스터 안 주소로 접속. Pod가 죽으면 K8s가 다시 띄우지만, 디스크·백업·버전업은 우리가 챙겨야 한다. 이미 켜 둔 노드 안에서 돌아 추가 요금은 거의 없다.
  • 멘토 타협안(10/28): RDB는 매니지드 OK, Redis·Airflow·ML 컴포넌트는 직접. 쿠버 운영을 배우고 비용을 줄이려는 것이다. [멘토]

8-7. [인프라 구성도와 카탈로그] 새로 만든 것

  • 2부 인프라 구성도: v1(인프라_대응도)과 같은 스타일. 멘토 언급은 보라색 테두리, MVP/확장 알약, 직접/매니지드 알약, 빨간 "추가"는 v1 카탈로그에 없던 멘토 언급(Helm, Redis 직접 설치안, 로깅 서버, 기사 검수 에이전트).
  • 인프라_툴_카탈로그_멘토기준_v2.md / .html: 76 → 84개. 추가 8, 조정 1(Memorystore 확장→미정).
  • 이름 규칙: 날짜보다 내용 + 판 번호(_v2)가 낫다. 날짜는 "무엇이 달라졌는지"를 알려 주지 않기 때문이다. 날짜는 파일 안의 변경 이력에 적는다. v1은 그대로 둔다.
