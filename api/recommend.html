추천 API 명세 · REC001 추천 피드 조회

초안입니다(합의 전). 내용이 정해지면 이 페이지와 Swagger를 같이 고칩니다. 아직 클러스터에 배포되지 않았습니다.

WAS가 부르는 API는 이것 하나입니다. 상태 확인 API(/healthz, /readyz)는 쿠버네티스가 쓰므로 WAS는 부르지 않습니다. 화면으로 보기: Swagger · OpenAPI 파일

개요 및 처리 규칙

  • 독자 1명의 추천순 피드를 size개(기본 20)씩 돌려줍니다.
  • 추천 서버가 후보 선정, 점수 계산, 정렬, 페이지 나누기, 페이지 간 중복·누락 방지를 모두 합니다. WAS는 후보를 고르지 않습니다.
  • 후보: 지금은 해당 분류에서 최근 7일 안에 발행된 최신 기사 200개입니다. 후보 목록은 매시 갱신되고, 추천 서버는 5분마다 다시 읽습니다.
  • 첫 조회 때 정렬한 목록을 30분 동안 보관합니다. 다음 페이지는 그 목록에서 이어서 꺼내므로 중간에 새 기사가 들어와도 중복·누락이 없습니다.
  • 최신순·조회수순·좋아요순은 WAS가 DB에서 직접 조회합니다. 이 API는 추천순에만 씁니다.

오류 응답

HTTP 상태구분응답 형태 / 의미 / 처리
400요청 검증 실패필드가 없거나 범위 밖입니다(예: size=0). {"error": "틀린 이유", "field": "body.size"} · 코드 버그이므로 오류 로그를 남깁니다.
400cursor 만료·불일치field가 "body.cursor"입니다. 30분이 지났거나, 첫 조회와 다른 reader_id·category·subcategory로 보냈거나, 값이 깨진 경우입니다. cursor 없이 첫 조회부터 다시 부릅니다.
503추천 서버 사용 불가{"detail": "not ready"}: 모델을 아직 못 읽음 · {"detail": "inference failed"}: 피처 조회·점수 계산 실패. 다른 정렬로 대체할지는 WAS가 정합니다.
—시간 초과·연결 실패503과 같이 처리합니다. 응답 시간 목표는 P99 200ms입니다(로컬 200개 기준 약 70ms, 클러스터는 배포 뒤 측정).

연결 메모

  1. 첫 조회: 프런트 → WAS(추천순·분류 조건) → WAS가 reader_id·category·subcategory·size=20으로 호출
  2. 받은 items 순서대로 기사 정보를 DB에서 가져와 응답을 만들고, 반환 기록에 score·model_version·position을 저장한 뒤 next_cursor와 함께 프런트에 응답
  3. 다음 조회: 프런트가 받은 next_cursor를 보내면 WAS가 같은 reader_id·category·subcategory와 cursor로 호출
  4. next_cursor가 null이면 더 줄 기사가 없습니다.
  5. 분류 조건을 바꾸거나 새로고침하면 cursor 없이 첫 조회부터 부릅니다.
  6. 400(body.cursor)이면 cursor 없이 첫 조회부터 다시 부릅니다. 503·시간 초과·연결 실패면 추천 결과 없이 처리합니다.
